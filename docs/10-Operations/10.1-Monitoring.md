## 1. Monitoring Stack Architecture

نهدف من خلال تصميم **نظام المراقبة (Monitoring Stack)** إلى تزويد المنصة بقدرة استشعار فائقة لرصد الأخطاء البرمجية، وتتبع تكاليف الذكاء الاصطناعي، ومراقبة جودة مخرجات RAG حياً لمنع الهلوسة، بالاعتماد على أدوات خفيفة بتكلفة صفرية:

```
                            ┌────────────────────────┐
                            │    Visitor Browser     │
                            └───────────┬────────────┘
                                        │ (HTTPS)
                                        ▼
    ┌───────────────────────────────────┴───────────────────────────────────┐
    │                                                                       │
    │  Sentry Error Logger ──► Cloud-managed Error tracking (Free Tier)     │
    │                                                                       │
    │  Uptime Robot ─────────► Outward availability monitoring (99.9% SLA)  │
    │                                                                       │
    │  PostgreSQL Telemetry ─► Logs costs, token usage, latencies, eval     │
    │                          passed flag for Admin Observability Panel.   │
    │                                                                       │
    └───────────────────────────────────────────────────────────────────────┘
```

## 2. Health Check Endpoints Specification

نعد رابطين برمجين لفحص صحة الخدمات بشكل دوري، ويتم استعلامهما كل 60 ثانية بواسطة Uptime Robot:

### 2.1 رابط صحة خادم الواجهة الخلفية (Backend: `/api/v1/health`):
- **النوع:** `GET`
- **آلية العمل:** يقوم بفحص نشاط واستجابة قاعدة البيانات PostgreSQL وذاكرة Redis.
- **جسم الاستجابة الناجحة (Success Response):**
```json
{
  "status": "healthy",
  "services": {
    "database": "connected",
    "redis": "connected"
  },
  "timestamp": "2026-07-06T12:49:18Z"
}
```
- **حالة الفشل:** يرجع الرد `503 Service Unavailable` مع تحديد الخدمة المعطلة لمساعدة المسؤول.

## 3. RAG Telemetry Logging (PostgreSQL & Sentry)

يتم تسجيل كل محادثة تجري بين الزوار ومساعد الذكاء الاصطناعي بدقة داخل جدول التتبع `InteractionLog` في قاعدة البيانات لرسم إحصائيات المسؤول:

- **البيانات المسجلة (Telemetry Schema):**
  - `query_tokens` / `completion_tokens`: عدد التوكنز المستهلكة في الموجه والإجابة.
  - `cost_usd`: التكلفة المالية الدقيقة للطلب بالاعتماد على تسعيرة OpenAI الحالية.
  - `latency_ms`: الوقت المستغرق منذ إرسال السؤال حتى بدء بث الكلمة الأولى.
  - `retrieved_chunks`: أرقام معرفات الفقرات المسترجعة لمراجعة جودة البحث لاحقاً.
- **تتبع الاستثناءات (Sentry Integration):**
  - عند حدوث أي خطأ برمجي غير متوقع (Uncaught exception)، يقوم Sentry بالتقاط الـ Stack Trace مع الـ Correlation ID آلياً وتنبيه المسؤول لمنع تكرار العطل.

## 4. Uptime SLA & Response Monitoring

- **هدف جاهزية الموقع (Uptime Target):** الالتزام بنسبة جاهزية لا تقل عن **99.9%** شهرياً.
- **فحص الكمون المستمر (Latency Monitoring):**
  - يقوم Uptime Robot بقياس زمن استجابة صفحة الهبوط.
  - إذا ارتفع متوسط تحميل الصفحة عن **1.5 ثانية**، يتم تسجيل عطل أداء مؤقت للتحقق من كفاءة CDN وكاش Edge Vercel.
