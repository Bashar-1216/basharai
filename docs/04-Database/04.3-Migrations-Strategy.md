## 1. Migration Philosophy & Ownership

لتجنب تضارب التعديلات وتلف البيانات عند استخدام لغتين برمجيتين (Node.js لـ Next.js و Python لـ FastAPI) للوصول لنفس قاعدة البيانات:

- **مالك المخطط (Schema Owner):** تطبيق Next.js هو المالك الوحيد لمخطط قاعدة البيانات عبر **Prisma Migrations**.
- **مستهلك المخطط (Schema Consumer):** يقرأ تطبيق FastAPI الجداول فقط ولا يحق له إجراء أي تعديلات هيكلية (No Write Schema permission).
- **العقد البرمجي (Database Contract):** يتم تخزين أي تعديل برميجي في المخطط داخل ملفات هجرة Git المتتابعة لضمان التوافق وتسهيل النشر الآلي.

## 2. Prisma Migrations Workflow

تتبع عملية ترحيل وتحديث قاعدة البيانات المسارات التالية بناءً على بيئة التشغيل:

### 2.1 في البيئة المحلية (Local Development):
1. يقوم المطور بإجراء التعديلات في ملف `schema.prisma`.
2. يتم تشغيل الأمر لتوليد ملف الهجرة وتحديث قاعدة البيانات المحلية:
   ```bash
   npx prisma migrate dev --name add-new-field
   ```
3. يقوم Prisma بإنشاء مجلد هجرة جديد يحوي ملف `migration.sql` ويتم دفعه إلى مستودع GitHub.

### 2.2 في بيئات Staging و Production (CI/CD Deployment):
يتم تشغيل الترقية تلقائياً كخطوة بناء سابقة للنشر (Pre-build stage) لضمان اتساق الجداول قبل تشغيل الأكواد الجديدة:
```bash
npx prisma migrate deploy
```
*يضمن هذا الأمر تشغيل ملفات SQL غير المطبقة فقط دون المساس ببيانات الجداول الأخرى.*

## 3. Zero-Downtime Schema Updates (Expansions & Contractions)

لتحديث الجداول دون التسبب في انقطاع الخدمة أو أخطاء استعلام (Zero Downtime) أثناء مرحلة الترقية الانتقالية:

نتبع نمط **التوسيع والتقليص (Expand and Contract)** لجميع العمليات الحساسة:

```
[Phase 1: Expand] ──► Add new column (nullable or with default)
                             │
                             ▼
[Phase 2: Transition] ──► Deploy new code that writes to both columns & syncs old data
                             │
                             ▼
[Phase 3: Contract] ──► Deploy code that reads only from new column & delete old column
```

### 3.1 تجنب الأخطاء الشائعة:
- **تغيير اسم حقل (Renaming Column):**
  - **الخطأ:** حذف العمود القديم وإنشاء عمود جديد بالاسم الجديد دفعة واحدة (يسبب خطأ 500 للمستخدمين النشطين أثناء البناء).
  - **الصحيح:** إضافة العمود الجديد أولاً كـ Nullable، تعديل الكود ليكتب في العمودين معاً، تشغيل سكربت لنسخ البيانات القديمة، ثم تعديل الكود ليقرأ من الجديد فقط، وأخيراً حذف القديم في عملية هجرة منفصلة لاحقاً.

## 4. Alembic/FastAPI DB Schema Sync

على الرغم من أن Prisma يدير المخططات، يحتاج تطبيق FastAPI لمعرفة شكل الجداول لقراءة وكتابة سجلات RAG والتقييمات.

- **الحل:**
  - نستخدم **SQLAlchemy Declarative Models** في FastAPI لمطابقة المخطط المعرف في Prisma.
  - لا نستخدم Alembic لتوليد ملفات هجرة في FastAPI لعدم ازدواجية الإدارة.
  - نختبر سلامة الاتصال وفهم الجداول آلياً في بيئة اختبارات FastAPI عبر تشغيل اختبارات تكاملية بسيطة (Integration Tests) تقرأ وتكتب في قاعدة بيانات تجريبية (Test DB) للتأكد من عدم وجود اختلاف في أسماء الحقول أو أنواعها بين الكودين.

## 5. Data Loss Mitigation & Backup Policy

- **نسخ احتياطية تلقائية (Automated Snapshots):**
  - يتم تهيئة خادم Supabase/Neon لعمل نسخة احتياطية يومية تلقائية مع الاحتفاظ بها لمدة 7 أيام.
- **تأكيد ملفات الهجرة قبل تشغيلها (Pre-migration audit):**
  - يُمنع تشغيل أي ملف هجرة SQL يدوياً ضد قاعدة بيانات الإنتاج.
  - يجب التحقق من ملفات `migration.sql` المولدة محلياً ومراجعتها بدقة والتأكد من عدم احتوائها على أوامر `DROP COLUMN` أو `DROP TABLE` مدمرة قبل دمجها.

## 6. Rollback Sequence & Troubleshooting

في حال فشلت عملية ترحيل الجداول في الإنتاج أو تسببت في أخطاء تشغيلية:

1. **إلغاء الترقية فوراً (Abort Deploy):**
   - يتم إيقاف بناء خوادم Next.js و FastAPI لمنع إرسال أكواد لا تطابق المخطط الحالي.
2. **التراجع للمخطط السابق (Schema Rollback):**
   - في حال تعذر التراجع السريع، يتم تشغيل هجرة SQL عكسية (Down migration) يدوياً لإعادة الجداول لهيكلها المستقر.
3. **استعادة البيانات (Data Restore):**
   - كملجأ أخير، يتم استعادة آخر نسخة احتياطية (DB Snapshot) تم أخذها قبل بدء عملية النشر الفاشلة.
