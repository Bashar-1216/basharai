## 1. Error Handling Philosophy

لا تمنع البرمجيات الجيدة وقوع الأخطاء بالكامل، بل **تتعامل معها بنضج (Graceful Degradation)** وتضمن عدم توقف كامل الموقع عند فشل جزء منه. تعتمد استراتيجية معالجة الأخطاء في bashar.ai على المبادئ التالية:

- **لا استسلام للأخطاء (Never Crash the User):** إذا فشل RAG Assistant، يجب أن يظل بإمكان الزائر قراءة السيرة الذاتية ورؤية دراسات الحالة.
- **الوضوح البرمجي مقابل الغموض البصري:** نسجل الأخطاء بالتفصيل الفني خلف الكواليس (Correlation ID + Logs)، ولكن نقدم للمستخدم رسائل واضحة ومباشرة وثنائية اللغة دون تفاصيل تقنية محيرة.
- **الفشل الواضح (Fail-Fast) داخلياً:** تفشل الخدمات داخلياً بشكل صريح وفوري لتسهيل الكشف المبكر والتعافي السريع أثناء عملية التطوير.

## 2. Frontend Graceful Degradation

### 2.1 React Error Boundaries (Per-Section Isolation):
لا نستخدم Error Boundary عالمي يغطي كامل الصفحة. بدلاً من ذلك، نقوم بتغليف المكونات التفاعلية الأساسية (مثل لوحة تحليلات المسؤول، أو صندوق المحادثة الذكي) بحدود أخطاء مستقلة:
```tsx
// components/common/ErrorBoundary.tsx
import React, { Component, ErrorInfo, ReactNode } from "react";

export class SectionErrorBoundary extends Component<{children: ReactNode; fallback: ReactNode}> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error, errorInfo: ErrorInfo) {
    console.error("ErrorBoundary caught an error", error, errorInfo);
    // Log to structured DB Analytics via API
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback;
    }
    return this.props.children;
  }
}
```

### 2.2 Fallback UI Patterns:
- **Skeleton Loaders:** تظهر عند حدوث تأخير في التحميل لمنع CLS.
- **Retry Buttons:** نوفر أزرار "إعادة المحاولة" سهلة الاستخدام للتعافي الفوري دون الحاجة لتحديث كامل الصفحة (F5).

## 3. Backend Structured Errors (Unified API Contract)

لضمان معالجة متسقة للأخطاء بين Next.js BFF و FastAPI، نعتمد صيغة إرجاع موحدة للأخطاء (Unified JSON Error Schema) باللغتين العربية والإنجليزية:

```json
{
  "error": {
    "code": "CHAT_RATE_LIMITED",
    "message_en": "You have reached the maximum number of chat requests. Please try again after {retry_after} seconds.",
    "message_ar": "لقد وصلت إلى الحد الأقصى لطلبات المحادثة. يرجى المحاولة بعد {retry_after} ثانية.",
    "retry_after": 45,
    "correlation_id": "err_req_90b2c140df"
  }
}
```

### FastAPI Global Exception Handler:
```python
from fastapi import Request, status
from fastapi.responses import JSONResponse

@app.exception_handler(AppBaseException)
async def custom_exception_handler(request: Request, exc: AppBaseException):
    return JSONResponse(
        status_code=exc.status_code,
        content={
            "error": {
                "code": exc.code,
                "message_en": exc.message_en,
                "message_ar": exc.message_ar,
                "correlation_id": request.state.correlation_id
            }
        }
    )
```

## 4. LLM & AI Layer Fault Tolerance

تعتبر الاتصالات بالـ APIs الخارجية (مثل OpenAI) هي النقطة الأكثر عرضة للفشل أو البطء.

1. **إعادة المحاولة التلقائية (Exponential Backoff with Jitter):**
   - عند حدوث فشل مؤقت في OpenAI (مثل خطأ HTTP 503 أو 429 مؤقت)، يعيد النظام المحاولة تلقائياً بزيادة وقت الانتظار أسياً مع إدخال نسبة عشوائية (Jitter) لمنع تفاقم الضغط على خوادم OpenAI.
2. **استراتيجية التراجع النموذجي (Model Degradation Fallback):**
   - إذا فشل نموذج GPT-4o أو واجه قيود استهلاك حادة (Rate limit)، يتراجع النظام برمجياً وبشكل صغير (Fallback) لاستخدام `GPT-4o-mini` بشكل تلقائي لضمان استمرارية الخدمة.
3. **أخطاء البث المباشر (Mid-Stream Errors):**
   - إذا حدث انقطاع في الاتصال أثناء بث الإجابة (SSE)، يتم إرسال إشارة إغلاق خاصة `[ERROR]` في مجرى البث ليقوم كود المتصفح بإغلاق الاتصال بأمان وعرض تنبيه مناسب للمستخدم عوضاً عن البقاء في حالة انتظار دائم.

## 5. RAG-Specific Failures & Fallbacks

- **السيناريو 1: لم يتم العثور على وثائق كافية (No relevant docs found):**
  - **السلوك:** بدلاً من محاولة النموذج التخمين أو الهلوسة، نوجه الموجه البرمجي (System Prompt) للإجابة بـ: "عذراً، لم أجد معلومات حول هذا السؤال في الوثائق المتاحة. أنا متخصص في الإجابة عن خبرة بشار وماري الهندسية ومشاريعهما الذكية فقط".
- **السيناريو 2: توقف محرك التضمين (Embedding service down):**
  - **السلوك:** إذا فشل توليد Embedding لسؤال المستخدم، يتراجع النظام تلقائياً للبحث النصي التقليدي (Keyword Search via BM25) لتقديم سياق تقريبي بدلاً من إيقاف الخدمة كلياً.
- **السيناريو 3: تجاوز نافذة السياق (Context window exceeded):**
  - **السلوك:** يقوم FastAPI بقطع المحادثات الأقدم في الذاكرة والاحتفاظ بالرسائل الأخيرة فقط تلقائياً للالتزام بالحد الأقصى المتاح للنموذج.

## 6. Error Taxonomy (Standard Codes)

نحدد قائمة موحدة بأكواد الأخطاء الشائعة لتسهيل الفحص والتحليل في لوحة المراقبة:

| Error Code | HTTP Status | Description | User Message (AR) |
|------------|-------------|-------------|-------------------|
| **AUTH_UNAUTHORIZED** | 401 | Invalid or missing admin session. | غير مصرح لك بالوصول لهذه الصفحة. |
| **CHAT_RATE_LIMITED** | 429 | Visitor exceeded token limit. | تم تجاوز الحد المسموح به. يرجى المحاولة لاحقاً. |
| **LLM_TIMEOUT** | 504 | OpenAI API call timed out. | استغرق مزود الذكاء الاصطناعي وقتاً أطول للاستجابة. |
| **RAG_DB_ERROR** | 500 | pgvector database query failed. | حدث خطأ أثناء البحث في سياق الوثائق. |
| **VALIDATION_ERROR** | 422 | Input JSON failed schema check. | البيانات المرسلة غير صالحة. |

## 7. User-Facing Experience (Offline, 404, 500, 429)

- **صفحات 404 المخصصة:**
  - واجهة ثنائية اللغة جميلة تقترح على المستخدم مسارات بديلة بدلاً من تركه تائهاً (مثل الذهاب لصفحة المشاريع أو السيرة الذاتية).
- **صفحات الأخطاء العامة (500):**
  - واجهة تعتذر بلطف وتوفر خياراً للزائر لإرسال تقرير الخطأ آلياً مع طباعة الـ Correlation ID لتسهيل التحقق.
- **مؤشر وضع عدم الاتصال (Offline Detection):**
  - إذا فقد المستخدم اتصاله بالإنترنت، يظهر تنبيه صغير يعلمه بأنه يتصفح حالياً النسخة المخزنة مؤقتاً (Cached Version) وأن بعض الوظائف (مثل الـ RAG Assistant) قد لا تكون متاحة حتى استعادة الاتصال.
