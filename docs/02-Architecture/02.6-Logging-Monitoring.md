## 1. Logging & Monitoring Overview

تُعد المراقبة والتحليل جزءاً لا يتجزأ من **المشروع البرمجي الرائد الثاني (Epic E2)**. لا تقتصر معمارية السجلات والمراقبة هنا على تتبع أخطاء النظام، بل تمتد لتسجيل أداء أنظمة الذكاء الاصطناعي بدقة متناهية وعرض هذه البيانات للزوار في شاشة تفاعلية تثبت كفاءة المرشح في إدارة جودة وميزانية الـ LLM في بيئات الإنتاج الحقيقية.

## 2. Application Logging Architecture

نعتمد على **السجلات المهيكلة (Structured Logging)** بصيغة JSON لتسهيل التحليل والبحث البرمجي.

- **الواجهة الخلفية (FastAPI):**
  - نستخدم مكتبة `loguru` لتهيئة السجلات وتوحيد صيغة الإخراج.
  - نقوم بإلحاق معرف فريد للطلب (Correlation ID) بكل سجل لتتبع دورة حياة الطلب من الواجهة الأمامية وحتى قاعدة البيانات.
- **مستويات السجلات (Log Levels):**
  - `DEBUG`: للمعلومات التطويرية التفصيلية (يتم إيقافها في الإنتاج).
  - `INFO`: للعمليات الطبيعية (تسجيل طلبات الـ API الناجحة).
  - `WARNING`: للحالات غير الطبيعية التي لا توقف النظام (مثل تراجع سرعة استجابة OpenAI).
  - `ERROR`: للأخطاء البرمجية والبرمجيات الوسيطة التي تفشل في معالجة الطلب (تفعيل تنبيهات فورية).
  - `CRITICAL`: عند توقف مكون أساسي (مثل تعذر الاتصال بالكامل بقاعدة البيانات).

## 3. LLM Observability Engine (Feeds Epic E2)

لتحقيق متطلبات لوحة التحكم التفاعلية (Epic E2)، يقوم النظام بتسجيل المقاييس التالية لكل عملية تفاعل مع المساعد الذكي:

| Metric Category | Specific Metrics Recorded | Purpose |
|-----------------|---------------------------|---------|
| **Compute & Cost** | • Input/Output Tokens<br>• Real API Cost (USD)<br>• Model version used | Tracks resource spending and highlights optimizations (like prompt compression). |
| **User Experience** | • Time-to-First-Token (TTFT)<br>• Total Latency (ms)<br>• Conversation Length | Monitors performance and spots latency degradations in the GCC region. |
| **RAG Quality** | • Retrieve similarity scores<br>• Chunks IDs used<br>• Language detection code | Analyzes semantic search efficiency and cross-language retrieval quality. |
| **Evaluation Metrics**| • RAG Triad scores (Context Relevance, Groundedness, Answer Relevance) | Proves production-readiness of the LLM pipeline. |

## 4. Monitoring Stack Decision

اتخذنا قرارًا باستخدام **نموذج المراقبة المزدوج (Dual Monitoring Model)**:

1. **النموذج المخصص للمستخدمين (Custom DB-backed Logs):**
   - يتم تخزين مقاييس الـ LLM الأساسية مباشرة في قاعدة بيانات PostgreSQL في جداول تحليلات مخصصة.
   - **السبب:** هذا يسمح للوحة التحكم التفاعلية الخاصة بنا (Epic E2) بالاستعلام عن البيانات محلياً وعرضها في زمن حقيقي دون تكلفة أو تأخير للزوار.
2. **أداة المطور المتقدمة (LangSmith):**
   - ندمج `LangSmith` عبر متغيرات البيئة لجمع سجلات وتفاصيل مسار RAG (Traces) بشكل تفصيلي.
   - **السبب:** يوفر LangSmith واجهة فحص ممتازة للمطور أثناء التطوير لتقصي الأخطاء وحساب تراجع أداء التوليد (Regression) دون جهد برمجي إضافي.

## 5. Evaluation Dashboard Data Pipeline

يمثل المخطط التالي تدفق البيانات وتحديث مقاييس لوحة المراقبة:

```
[LLM Interaction] ──► [FastAPI Middleware] ──► [Async Background Task]
                                                        │
                                                        ▼
[Custom Dashboard Page] ◄── [Query API] ◄── [PostgreSQL Analytics DB]
```

1. **التسجيل غير المعيق (Non-blocking Logging):**
   - بعد انتهاء إجابة RAG وبثها للمستخدم، يقوم FastAPI بتمرير بيانات التتبع كـ `BackgroundTasks` ليتم حفظها في قاعدة البيانات بشكل خلفي دون إعاقة استجابة الزائر.
2. **التحديث الدفعي للتقييمات (Batch Evaluation Runs):**
   - نقوم بتشغيل اختبارات تلقائية دورية (Cron Job أو زر تشغيل يدوي للمسؤول) تقوم بتشغيل مجموعة الأسئلة الذهبية (Golden Set) ضد RAG Engine وتسجيل نسبة النجاح العامة وتاريخ التشغيل في جدول `evaluation_results` لعرض اتجاهات جودة النظام بمرور الوقت.

## 6. Application Performance Metrics (APM)

إلى جانب مقاييس الـ LLM، نراقب المقاييس الصحية الأساسية للتطبيق:
- **API Response Times (p50, p95, p99):** زمن استجابة خوادم FastAPI.
- **Error Rates:** نسبة الأخطاء (4xx و 5xx) مقارنة بإجمالي الطلبات.
- **Database Connection Pool:** مراقبة الاتصالات النشطة لمنع استهلاك حدود قاعدة البيانات على بيئة Supabase/Neon المجانية.
- **Redis Memory Usage:** التأكد من عدم تجاوز مساحة الكاش والـ Rate Limiting المخصصة.

## 7. Alerting & Incident Strategy

نظراً لإدارة الموقع بواسطة مطور منفرد، يتم تقليص التنبيهات لتصل عبر قنوات مجانية ومريحة:
- **تنبيهات البريد الإلكتروني (Resend / SMTP):** عند حدوث أخطاء من مستوى `CRITICAL` أو `ERROR` متكررة في خوادم الإنتاج.
- **LangSmith Alerting:** إرسال إشعارات في حال تجاوز استهلاك OpenAI لميزانية محددة مسبقاً (Budget alert).

## 8. Privacy & Security (PII Sanitization)

لحماية خصوصية الزوار ومطابقة القوانين الأمنية (PRD §10):
- **تنظيف السجلات (Sanitization):** يُمنع تسجيل أي معلومات شخصية للزوار (PII) مثل الأسماء أو البريد الإلكتروني أو كلمات المرور في جداول التحليلات العامة.
- **معالجة نصوص المحادثات:** يتم فحص نصوص الاستعلامات آلياً لإزالة العناوين أو الأرقام الحساسة (مثل أرقام الهواتف أو بطاقات الائتمان) قبل كتابتها في السجلات الدائمة.
