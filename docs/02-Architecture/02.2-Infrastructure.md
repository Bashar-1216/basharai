## 1. Deployment Architecture

تم تصميم البنية التحتية لتكون **منفصلة وموزعة (Decoupled & Distributed)** لتحقيق أفضل توازن بين السرعة والأداء للجمهور في الخليج العربي (GCC)، مع الالتزام التام بحدود التكلفة الصفرية في المراحل الأولى (Free-tier-first).

```
                            ┌──────────────────┐
                            │   DNS Registrar  │
                            │    (bashar.ai)   │
                            └────────┬─────────┘
                                     │
                  ┌──────────────────┴──────────────────┐
                  │ (CNAME / ALIAS)                     │ (A / CNAME)
                  ▼                                     ▼
        ┌──────────────────┐                  ┌──────────────────┐
        │  Vercel CDN Edge │                  │ Railway Router   │
        │   (PoP in UAE)   │                  │ (AWS Frankfurt)  │
        └────────┬─────────┘                  └────────┬─────────┘
                 │                                     │
                 ▼                                     ▼
        ┌──────────────────┐                  ┌──────────────────┐
        │  Next.js App     │                  │  FastAPI Backend │
        │  (Static/SSR)    │                  │  (Docker Engine) │
        └──────────────────┘                  └────────┬─────────┘
                                                       │
                                            ┌──────────┴──────────┐
                                            ▼                     ▼
                                  ┌──────────────────┐  ┌──────────────────┐
                                  │ Supabase/Neon DB │  │   Upstash Redis  │
                                  │ (PostgreSQL 16)  │  │  (Session/Cache) │
                                  └──────────────────┘  └──────────────────┘
```

## 3. GCC Region Latency Optimization

أحد أكبر التحديات في الخليج العربي هو **زمن الاستجابة (Latency)** مقارنة بالخوادم الموجودة في أوروبا أو أمريكا. تم التعامل مع هذا التحدي بالاستراتيجيات التالية:

1. **Vercel Edge Network:**
   - يمتلك Vercel نقاط حضور (Points of Presence - PoPs) في **دبي (UAE)** و**المنامة (Bahrain)**.
   - يتم تقديم الملفات الثابتة (Static Assets) وصفحات الـSSG مباشرة من خوادم الخليج في زمن استجابة يقل عن **30ms**.

2. **Backend Server Location (Railway):**
   - سيتم نشر تطبيق FastAPI وقاعدة البيانات في منطقة **أوروبا الوسطى (Frankfurt - eu-central-1)**.
   - تمثل فرانكفورت أفضل نقطة عبور كابلات بحرية دولية من الخليج العربي، حيث يتراوح زمن الاستجابة (RTT) بين الرياض/دبي وفرانكفورت بين **80ms إلى 110ms** وهو مقبول جداً لعمليات الـAI.

3. **Hybrid Search Data Locality:**
   - من خلال وضع ملفات الـEmbeddings في نفس قاعدة البيانات (pgvector في Supabase) بدلاً من خدمة منفصلة مثل Pinecone، نوفر رحلة شبكة كاملة (Round Trip) لكل طلب RAG.

## 5. Environment Strategy

نتبع استراتيجية بيئات ثلاثية بسيطة وفعالة لدعم المطور المنفرد:

```
┌────────────────────────┐      ┌────────────────────────┐      ┌────────────────────────┐
│      Development       │ ───► │        Staging         │ ───► │       Production       │
│  • Local Docker Engine │      │  • Vercel Preview PRs  │      │  • Main Domain Live    │
│  • Hot Reload / Local  │      │  • Railway Staging App │      │  • Production DB/Redis │
└────────────────────────┘      └────────────────────────┘      └────────────────────────┘
```

1. **البيئة المحلية (Development):**
   - تستخدم Docker Compose لتشغيل PostgreSQL (مع pgvector) وRedis محلياً لضمان مطابقة بيئة الإنتاج بالكامل دون الحاجة لاتصال بالإنترنت.
2. **بيئة المعاينة (Staging):**
   - يتم بناؤها تلقائياً مع كل Pull Request في GitHub على Vercel وRailway. تُستخدم للمراجعة والتحقق قبل الدمج في الفرع الرئيسي (master/main).
3. **بيئة الإنتاج (Production):**
   - هي البيئة الحية التي تخدم الزوار وتتصل بقاعدة البيانات الحية المدعومة بـ HNSW Indexes لعمليات البحث المتجهي.

## 6. Static Assets & CDN Strategy

تعتمد منصة bashar.ai بشكل كبير على التوليد الثابت (SSG) لركائز المحتوى (خبرة العمل، المشاريع، المدونة).

- **Asset Cache-Control:**
  - يتم إرسال ملفات الصور والخطوط بـ headers صارمة: `Cache-Control: public, max-age=31536000, immutable`.
- **i18n CDN Routing:**
  - يتم توجيه طلبات المتصفح بناءً على اللغة المفضلة مباشرة عند طبقة CDN (Edge Middleware) مما يلغي فترات الانتظار التي تحدث عند التحويل من اللغات LTR إلى RTL.
- **Image Optimization:**
  - يقوم Vercel بتغيير حجم الصور وتحويلها إلى صيغ WebP/AVIF تلقائياً بناءً على متصفح المستخدم وحجم شاشته، مما يقلل من حجم البيانات المنقولة بنسبة تصل إلى **75%**.

## 7. Alternatives Considered & Rejected

| Alternative Stack | Strengths | Why Rejected |
|-------------------|-----------|--------------|
| **AWS (ECS + RDS + Elasticache)** | Enterprise-grade, maximum control, local GCC regions (AWS Bahrain/Saudi) | Too expensive for starting ($100+/mo baseline), extremely high operational overhead for a solo developer. |
| **Render** | Great alternative to Railway, has a good free tier | Cold starts on the free tier for web services (up to 50 seconds delay) would ruin the RAG Assistant experience. |
| **Fly.io** | Runs containers close to users, global deployment | Harder migration/ops overhead, recent database reliability concerns in the community, complex pricing. |
| **DigitalOcean** | Standard VPS, predictable cost | No native free tier, requires manual server hardening, OS updates, and backup scripting (wastes developer time). |

## 9. Infrastructure as Code (IaC)

نظرًا لأن هذا المشروع يُدار بواسطة **مطور واحد** ويهدف إلى تقليل التعقيد التشغيلي:
- **لا نستخدم Terraform أو Pulumi** في هذه المرحلة.
- نعتمد على **Declarative Config Files** الخاصة بالمنصات:
  - `railway.json` لتعريف متطلبات تشغيل الـ Backend على Railway.
  - `docker-compose.yml` للتطوير المحلي.
  - Vercel UI لتهيئة إعدادات النشر المباشر.

يضمن هذا الأسلوب توثيق البنية التحتية في مستندات برمجية دون زيادة التعقيد أو استهلاك الوقت التشغيلي غير المبرر.
