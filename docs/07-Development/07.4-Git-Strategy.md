## 1. Branching Model (Trunk-Based Development)

نظراً لتطوير المشروع بواسطة مطور منفرد (Solo Developer) وبالتعاون مع مساعد الذكاء الاصطناعي، نعتمد استراتيجية **التطوير المعتمد على الجذع المشترك (Trunk-Based Development)** كبديل عن GitFlow المعقد.

### مميزات Trunk-Based Development:
- فرع رئيسي واحد مستقر ودائم النشاط (`master` أو `main`).
- إنشاء فروع قصيرة العمر (Short-lived feature branches) تدمج فوراً في الجذع بعد نجاح فحص الـ CI.
- تقليل احتمالية حدوث مشاكل دمج الكود المتأخرة (Merge Conflicts).
- تفعيل **أعلام المزايا (Feature Flags)** لعزل الميزات غير المكتملة في الإنتاج دون إعاقة دمج الكود.

## 2. Branch Naming Conventions | تسمية الفروع

تتم تسمية الفروع ببادئات صريحة توضح طبيعة التعديل:

| Branch Prefix | Example Branch Name | Purpose |
|---------------|---------------------|---------|
| `feat/` | `feat/rag-streaming` | Introducing a new functional feature. |
| `fix/` | `fix/ar-font-overflow` | Repairing a bug or styling overflow issue. |
| `docs/` | `docs/sprint-planning` | Modifying or creating documentation files. |
| `refactor/` | `refactor/api-response-types`| Code restructuring without changing behaviour. |
| `chore/` | `chore/update-ruff-config` | Updating settings, dependencies, or pipeline files. |

## 3. Commit Message Formatting (Semantic Commits)

نلتزم بكتابة رسائل commit منظمة وواضحة (Semantic Commits) لسهولة قراءة تاريخ المشروع وتوليد سجل التغييرات (Changelog) تلقائياً:

### الصيغة المعتمدة (Commit Format):
```
[PHASE-XX] type: brief description of changes (max 72 chars)
```
- **PHASE-XX:** يشير للمرحلة الحالية من مراحل المشروع العشرة (مثال: `[PHASE-02]` أو `[PHASE-07]`).
- **Type:** يتبع معايير Conventional Commits (`feat`, `fix`, `docs`, `refactor`, `chore`, `test`).

### أمثلة صحيحة (Good Examples):
- `[PHASE-02] docs: write infrastructure selection and latency strategy`
- `[PHASE-05] feat: implement SSE streaming response in FastAPI APIRouter`
- `[PHASE-08] test: add unit tests for recursive text splitter chunking logic`

## 4. Pull Request & Review Process

على الرغم من العمل المنفرد، يتم الالتزام بفتح Pull Request (PR) لكل ميزة لضمان تشغيل خط النشر الاستكشافي:

```
Create short-lived branch ──► Push commits ──► Open PR in GitHub
                                                    │
                                                    ▼
Merge to master ◄── Approve Preview URL ◄── GHA (Verify Lints & Tests Pass)
```

1. **فحص الـ CI التلقائي:** يقوم GitHub Actions بفحص جودة الكود وتأكيد نجاح الاختبارات.
2. **معاينة البيئة (Preview Deploy):** يتم مراجعة الـ Preview URL المولّد تلقائياً من Vercel للتأكد من المظهر والتجاوب البصري قبل دمج الكود نهائياً.

## 5. NDA & Confidentiality Pre-Merge Checklist

لحماية معلومات الشركات السابقة ومنع التسريبات العشوائية (أهم مخاطر المشروع)، يجب التحقق من قائمة فحص السرية (Confidentiality Checklist) في وصف كل PR قبل الدمج:

```markdown
<!-- Pull Request Template Checklist snippet -->
- [ ] NO proprietary internal system names, codes, or credentials committed.
- [ ] All metrics and impact results framed in high-level/general terms.
- [ ] No internal source code files or architecture drawings from past employers included.
- [ ] Tested pgvector indexing; no confidential data in generated seed files.
```

يضمن هذا الالتزام الصارم صيانة سمعة المرشح والتزامه التام باتفاقيات عدم الإفصاح الموقعة.
